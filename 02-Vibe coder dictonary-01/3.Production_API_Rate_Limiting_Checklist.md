# Production API Rate Limiting Checklist & Master Prompt

A comprehensive pre-launch audit, technical implementation guide, and AI agent prompt for securing vibe-coded and production APIs against brute force, credential stuffing, scraping, and resource exhaustion.

---

## The Core Rules

1. **Layered identity:** Never rely on IP address alone. Attackers rotate IPs via proxies and botnets, while thousands of legitimate users may share a single corporate NAT or mobile gateway. Use combined keys (e.g., `IP + normalized username/email` for auth, `UserID` or `API Key` for authenticated traffic).
2. **Atomic, distributed state:** For apps running on multiple instances or serverless platforms, in-memory counters (e.g. process memory) fail immediately. Use an atomic, centralized store (such as Redis or Upstash) with sliding-window algorithms.
3. **No information leakage:** Never disclose account existence in rate-limit errors or authentication responses. Return consistent error structures and generic messages.
4. **Defense in depth:** Rate limiting controls application-level abuse. It does not replace network DDoS mitigation (e.g., Cloudflare), authentication, authorization, or strict input validation.

## 1. Pre-Implementation Architecture Audit

- [ ] **Runtime & Framework:** Identify the backend stack (Node.js/Express, Next.js, Fastify, Python/FastAPI/Django, Go, Ruby on Rails) and deployment target (single VM, Docker container, Kubernetes, AWS Lambda, Vercel).
- [ ] **Single vs. Multi-Instance:** Determine if traffic is handled by multiple processes or instances. If more than one instance exists or serverless autoscaling is used, configure an external shared store (Redis).
- [ ] **Reverse Proxy & Ingress:** Identify upstream proxies (Cloudflare, Nginx, AWS ALB, Traefik).
- [ ] **Proxy Header Trust:** Explicitly configure trusted proxy hops. Never trust arbitrary `X-Forwarded-For` or `Client-IP` headers directly from untrusted clients to prevent IP-spoofing bypasses.
- [ ] **Inventory All Endpoints:** Catalog every REST route, GraphQL query/mutation, Server Action, and RPC method along with its HTTP verb and cost profile.
- [ ] **Existing Defenses:** Check for existing rate-limiting packages, WAF rules, or cloud gateway policies to prevent conflicting or duplicate counter enforcement.

## 2. Authentication & High-Risk Endpoints

Sensitive authentication endpoints require stricter, multi-layered rate limits:

### Login & Sign-in
- [ ] Limit failed login attempts per account identifier (e.g., 5 failed attempts per 15 minutes).
- [ ] Limit total login attempts per source IP (e.g., 20 attempts per 15 minutes) to mitigate credential stuffing across multiple accounts.
- [ ] Apply progressive delays (tarpitting) or CAPTCHA triggers on repeated failed attempts.

### Signup & Registration
- [ ] Limit new account creation per IP/subnet (e.g., 3-5 registrations per hour) to stop automated bot account farms.
- [ ] Require email verification or proof-of-work before granting full API resource creation privileges.

### Password Reset & Recovery
- [ ] Limit reset requests per account identifier (e.g., max 3 requests per hour).
- [ ] Limit reset requests per source IP to prevent email spamming and service exhaustion.
- [ ] Return identical generic success responses ("If an account exists, a reset link has been sent") to prevent user enumeration.

### OTP & Verification Codes
- [ ] Limit code generation/resend requests (e.g., 1 resend per 60 seconds; max 3-5 per hour).
- [ ] Limit code verification attempts per code/session (e.g., max 3-5 wrong guesses before invalidating the code completely).

### Token Refresh & Session Endpoints
- [ ] Enforce rate limits on token refresh endpoints (e.g., 30 requests per minute per session) to detect token replay or stolen session abuse.
- [ ] Invalidate refresh token families upon detected concurrent reuse anomalies.

### Zero Secret Logging
- [ ] Confirm that passwords, OTP codes, bearer tokens, and refresh tokens are **never** logged in rate-limiting logs or debug events.

## 3. HTTP Method & Route Cost Audit

Tailor limits based on computational, database, or external financial cost rather than treating all endpoints equally:

| Category | Typical Routes | Abuse Risk | Recommended Identity Key | Default Window & Limit |
| :--- | :--- | :--- | :--- | :--- |
| **Auth: Sensitive** | `/api/auth/login`, `/api/auth/reset-password`, `/api/auth/verify-otp` | Credential stuffing, brute force, enumeration | IP + Normalized Username / Account ID | 5 requests / 15 mins (strict) |
| **Auth: Token Refresh** | `/api/auth/refresh` | Replay attacks, session hijack | Session ID / Refresh Token Hash | 30 requests / 1 min |
| **Auth: Account Creation** | `/api/auth/register` | Automated bot creation, spam | IP Address / Device Fingerprint | 3-5 requests / 1 hour |
| **Resource Creation (POST)** | `/api/v1/posts`, `/api/v1/messages`, `/api/v1/invites` | Spamming, DB bloat, notification abuse | User ID (or IP if unauthenticated) | 20-30 requests / 1 min |
| **Expensive Reads (GET)** | `/api/v1/search`, `/api/v1/reports`, `/api/v1/export` | DB CPU spikes, full table scans, data scraping | User ID / API Key / IP | 10-20 requests / 1 min |
| **Standard Reads (GET)** | `/api/v1/items`, `/api/v1/profile` | Scraping, general traffic | User ID / IP | 100-300 requests / 1 min |
| **Mutations (PUT/PATCH)** | `/api/v1/users/profile`, `/api/v1/items/:id` | State churn, race conditions | User ID | 30-60 requests / 1 min |
| **Destructive (DELETE)** | `/api/v1/items/:id`, `/api/v1/account` | Mass deletion, destructive scripts | User ID | 10-20 requests / 1 min |
| **Public Unauthenticated** | `/api/v1/public/*`, `/api/v1/contact` | Bot scraping, spam | Client IP (trusted proxy resolved) | 60 requests / 1 min |
| **Internal & Webhooks** | `/api/webhooks/*` | Replay attacks | HMAC signature + Timestamp check | 1000 requests / 1 min (high burst) |

## 4. Technical Implementation & Storage Rules

- [ ] **Algorithm Selection:** Use a **Sliding Window Counter** or **Token Bucket** algorithm. Avoid fixed-window counters where double-limit bursts can occur across window boundaries.
- [ ] **Distributed Atomic Storage:** Use Redis, Valkey, or Upstash. Execute counter increments and expiration checks using atomic Lua scripts or multi-key atomic transactions to prevent race conditions.
- [ ] **Automatic Key Expiration (TTL):** Every rate-limit key stored in Redis must have a strict TTL matching the window duration to prevent unbounded memory leaks.
- [ ] **Canonicalize Route & Method:** Normalize endpoints (strip trailing slashes, enforce lowercase paths) to prevent bypasses such as `/api/login/` vs `/api/login`.
- [ ] **Exclude Health Checks & Preflights:** Exclude CORS preflight (`OPTIONS`) requests and internal orchestrator probes (`/healthz`, `/ready`) from rate-limiting counters.

## 5. HTTP Response Standards & Headers

When a request exceeds the configured threshold:

- [ ] Return status code **`HTTP 429 Too Many Requests`**.
- [ ] Provide the **`Retry-After`** header indicating the wait time in seconds:
  ```http
  HTTP/1.1 429 Too Many Requests
  Retry-After: 60
  Content-Type: application/json
  RateLimit-Limit: 100
  RateLimit-Remaining: 0
  RateLimit-Reset: 60
  ```
- [ ] Support IETF standard rate-limiting headers:
  - `RateLimit-Limit`: Maximum requests permitted in the current window.
  - `RateLimit-Remaining`: Remaining request quota.
  - `RateLimit-Reset`: Number of seconds until the quota resets.
- [ ] Return a safe, uniform JSON body:
  ```json
  {
    "error": {
      "code": "TOO_MANY_REQUESTS",
      "message": "Too many requests. Please try again later.",
      "retryAfter": 60
    }
  }
  ```
- [ ] Ensure error payloads never expose internal keys, stack traces, Redis connection details, or database IDs.

## 6. Infrastructure Resilience & Failure Modes

- [ ] **Failure Strategy Defined:** Determine what happens when Redis or the counter store is temporarily unreachable:
  - **Fail-Closed for Auth:** Authentication and password reset endpoints should fail closed (or fall back to strict local in-memory caps) during store outages to prevent unmonitored brute-force attacks.
  - **Fail-Open for Public Reads:** Ordinary, low-risk GET requests may fail open with high-priority alert logging to prevent taking the entire application offline during a cache blip.
- [ ] **Timeout Safeguards:** Keep Redis network timeouts short (e.g., 50–100ms) so rate-limiting checks do not stall normal API response pipelines if the cache degrades.
- [ ] **Circuit Breaking:** Gracefully degrade or trigger alerts if the shared storage failure rate exceeds 5%.

---

## 7. Observability, Metrics & Telemetry

- [ ] **Structured Logging:** Emit structured log entries whenever an HTTP 429 is triggered:
  - Event type: `rate_limit_exceeded`
  - Endpoint and method: `POST /api/auth/login`
  - Policy name: `auth_login_strict`
  - Masked or hashed identifier: SHA-256 of IP or User ID (never log raw secrets or sensitive emails)
  - Window and limit details
- [ ] **Metrics & Dashboards:** Track:
  - `rate_limit_hits_total` (counter, labeled by endpoint and policy)
  - `rate_limit_storage_latency_ms` (histogram)
  - `rate_limit_storage_errors_total` (counter)
- [ ] **Configurable Environment Variables:** Externalize all policies:
  ```env
  RATE_LIMIT_REDIS_URL="redis://localhost:6379"
  RATE_LIMIT_AUTH_MAX="5"
  RATE_LIMIT_AUTH_WINDOW_SEC="900"
  RATE_LIMIT_API_MAX="100"
  RATE_LIMIT_API_WINDOW_SEC="60"
  RATE_LIMIT_TRUST_PROXY="true"
  ```

## 8. Verification & Test Suite Requirements

Before marking rate limiting as production-ready, ensure automated tests verify:

- [ ] **Normal Traffic Test:** Requests below the threshold return `200 OK` (or expected status) with decrementing `RateLimit-Remaining` headers.
- [ ] **Threshold Exceeded Test:** The N+1 request immediately receives `HTTP 429` with valid `Retry-After`.
- [ ] **Window Expiry Test:** After the time window elapses, new requests succeed and quota is restored.
- [ ] **Concurrency / Race-Condition Test:** Sending 20 concurrent requests against a limit of 10 allows exactly 10 and rejects 10 without race condition leaks.
- [ ] **IP-Spoofing Immunity Test:** Sending forged `X-Forwarded-For: 1.2.3.4` headers from an untrusted client does not bypass limits or pollute other users' quotas.
- [ ] **User Isolation Test:** User A exceeding their limit does not impact User B.
- [ ] **Failure Mode Test:** When the rate-limiting store is mocked as offline, the application executes the defined fail-closed or fail-open policy safely.

## Copy-paste AI Master Prompt

Use this master prompt in Cursor, Claude Code, Antigravity, or your preferred AI coding agent:

```text
Act as a senior backend engineer and application security engineer. Audit my existing codebase and implement robust, production-ready rate limiting across all relevant APIs and authentication flows.

Do not just give me recommendations. Inspect the codebase, implement the changes, run the available tests, and report what you changed.

1. Inspect the Existing Application:
- Identify language, backend framework, API structure, database, auth mechanism, and deployment environment.
- Locate all API routes, controllers, middleware, server actions, and publicly accessible endpoints.
- Identify login, signup, password reset, OTP, token refresh, search, file upload, payments, and sensitive operations.
- Check whether the app runs on single/multiple instances, serverless, or behind a reverse proxy/gateway.
- Inspect existing rate-limiting libraries, middleware, and tests to avoid duplicate or conflicting implementations.
- Respect project coding conventions and architecture.

2. Protect Authentication Endpoints:
- Login: Limit failed attempts per IP and per account identifier to defeat password guessing and credential stuffing.
- Signup: Prevent automated bot account creation and abuse.
- Password reset: Limit requests per account and per source IP; prevent account enumeration with generic messages.
- OTP and verification codes: Limit code requests, verification attempts, and resends.
- Token refresh: Prevent excessive refresh requests and token abuse without breaking legitimate sessions.
- Zero secret logging: Never log passwords, tokens, OTPs, or secrets.

3. Audit Every API Method:
- GET: Protect expensive searches, data exports, scraping targets; do not needlessly restrict cheap reads.
- POST: Protect auth, resource creation, messaging, uploads, and transactional triggers.
- PUT/PATCH/DELETE: Protect against rapid updates or mass deletion.
- Public vs Authenticated: Apply network-level IP limits for public routes; apply user-aware keys for authenticated users.

4. Configurable Policies & Sensible Defaults:
- Define categories: Auth Strict, Token Refresh, Write/Mutations, Expensive Reads, General Public, and Internal/Webhooks.
- Provide sensible, configurable defaults (via environment variables).
- Use sliding window or token bucket algorithm.

5. Correct Implementation & Storage:
- Use a maintained library compatible with the stack.
- Use a shared, atomic storage mechanism (e.g. Redis) if multi-instance or serverless.
- Ensure counter updates are atomic under concurrent requests.
- Configure automatic TTL/expiry on all storage keys.
- Respect forwarded client IPs ONLY when set by explicitly trusted proxies.

6. Return Correct Responses:
- HTTP 429 Too Many Requests when limit is exceeded.
- Provide 'Retry-After' header and standard 'RateLimit-*' headers where supported.
- Return standard, safe JSON error format without leaking internal details or account existence.

7. Infrastructure & Failure Modes:
- Exclude CORS preflight (OPTIONS) and health checks (/health, /ready).
- Define fail-closed behavior for sensitive auth and fail-open with alerting for low-risk reads if storage is down.

8. Automated Tests:
- Write/update tests verifying: requests below limit succeed, requests over limit return 429, counters reset after window, concurrent requests cannot bypass counters, and spoofed headers are rejected.

9. Report:
- Summarize changes, protected endpoints, limits table, new dependencies/env vars, test execution results, and unresolved risks.
```

## Key Reminders

- **Rate limiting is not a complete anti-DDoS solution:** High-volume volumetric DDoS attacks must be filtered at the network edge (Cloudflare, AWS Shield, Fastly) before hitting application instances.
- **Do not rely on IP alone:** Mobile telecom towers and corporate VPNs route thousands of legitimate devices through identical public IPs. Combine IP with user identifiers whenever possible.
- **Fail-closed on security, fail-open on convenience:** If Redis goes down, protect authentication endpoints from brute force by failing closed, but allow read endpoints to fail open to prevent total service paralysis.
